## 6. 今後溜まらないための運用案（提案。実装していない）

1. **週1回の棚卸しの定期ジョブ**（例: 月曜の朝）。やることは読み取りと下書きまで:
   `harness-learn status`（開発台帳と運営者台帳の両方）→ `harness-curator.mjs` → `pattern suggest` → 上位の束を1つずつ pending に積む
   → 「人が見るもの」の短い一覧（pending の変更 id・記録だけ足りない id・退避候補）を出す。approve・apply・退避は人の手番に残す。
   エージェントの approve を許すかは別に決める（SKILL は許しているが、今回の依頼は人に残した）。
2. **取り込みの基準**:
   - 同じ評価項目・同じ趣旨が **3回以上、かつ別の日か別の台本（別の contract・別の Job）で** 出たものを最優先にする。同じ夜の品質ループの回の数は1回と数える
   - 2回以上でも実測の根拠（数値・SHA・テスト）があるものは次点
   - コードとテストで既に止まるものは正本の文にせず、退避候補として人へ回す
   - 1回目から関門にする種類（公開面の安全・人物の取り違え・課金・承認の詐称）は回数を待たない（既存の規則どおり）
3. **自動捕捉の数え方を直す**: 台本の品質ループは回ごとに session を作るので、捕捉の session を「ループ（作業フォルダ × 契約）」単位にする。
   そうすれば「×10」が独立した再発の数に近くなり、status の並びが意味を持つ。
4. **運営者側の学習を開発台帳へ戻す道を作る**: 今は新しい提案の本文が戻らない。運営者と開発者が同じ人の端末なら、運営者台帳の
   共有層を開発台帳へ取り込む読み取り専用の比較（差分の id と宛先の候補）を週次ジョブに入れ、人が選んだものだけ capture し直す。
   他人の端末は今どおり feedback bundle の同意（`new-candidates`）に限る。
5. **宛先の入口で付け替えを促す**: platform-craft 宛の capture のうち、YouTube の戦略・サムネ・アカウントの事情らしい語を含むものは
   「BuzzAssist の外のスキル向けでは？」と警告する（拒否はしない）。
6. **explainer に正本を作る**: 要求台帳（review-only）かジャンルの正本スキルが無い限り、台本の品質ループの自動捕捉は永遠に溜まる。
   最初の節は 2. の上位6項目で足りる。no-improvement で止まる回が5回あるので、上限・工程の順番も同時に見直す。
7. **運営者の端末の sync を動かす**: 検査語彙（digest と鍵）を運営者の端末に置く。無いあいだは運営者側の overlay が更新されない。
8. **チャンネルの保存先を status から見えるようにする**: 3 チャンネルの 78 件は、配置表 `config/harness-deployments.json` に
   channels が無いため `--channel` でも開けない。配置表へ登録するか、登録されていない保存先があることを status の末尾に出す。
